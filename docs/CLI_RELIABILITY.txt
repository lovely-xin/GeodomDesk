GeodomDesk CLI：连接复用、故障恢复与实践说明

适用范围
会话协议 session_protocol=2 复用加密连接，每条脚本使用独立进程。运行 --help 查看安装版参数，在 ready 中读取 session_protocol、cli_version 和 cli_build。

一、日常操作
1. 找到完整安装目录中的 geodomdesk-cli.exe（Windows）或 geodomdesk-cli（Linux）。不要单独复制启动器。
2. 先 probe 确认设备 ID、hostname、platform、terminal 能力和连接方式。默认 probe 不运行远端 Shell；probe --transport ssh 只验证 SSH 和协议准备，不发送用户脚本。
3. 偶尔运行命令使用 exec；每次 exec 都创建独立连接。连续操作启动一次 session 并保留三个管道。
4. 等待 ready，再写一行 JSON 并 flush。推荐一问一答，读取对应 id 的结果再提交下一条。
5. 始终排空 stdout 和 stderr。stdout 是 JSON Lines，结果中的 stdout/stderr 字段是 Base64 字节。

Windows 示例（DEVICE_ID、EXPECTED_HOST 请替换为实际值）：
$cli = 'C:\Program Files\GeodomDesk\geodomdesk-cli.exe'
& $cli probe --id DEVICE_ID --non-interactive --connect-timeout 30
& $cli exec --id DEVICE_ID --shell bash --command 'pwd' --json --non-interactive --timeout 15 --expect-platform Linux --expect-hostname EXPECTED_HOST
& $cli session --id DEVICE_ID --shell bash --non-interactive --timeout 15 --connect-timeout 30 --expect-platform Linux --expect-hostname EXPECTED_HOST

向 session 的标准输入逐行发送：
{"id":"check-1","script":"pwd"}
{"id":"check-2","script_file":"C:\\work\\check.sh","timeout":60}
{"id":"check-3","connection":"fresh","script":"pwd"}
{"id":"status-1","op":"status"}
{"id":"reset-1","op":"reconnect"}
{"id":"stop-1","op":"cancel"}
{"id":"close-1","op":"close"}

script_file 是发起端本机的普通文件路径，不接受命名管道或设备文件；管道内容可交给 exec --script -，会话则发送 script 文本。script 和 script_file 二选一。script_file 不能为 -。脚本以 UTF-8 编码，shell 按目标选择 bash、powershell 或已安装的 pwsh。Windows 管理员终端保留原有 --admin-user 验证流程。

二、连接控制
connection=fresh：给这条新请求创建新连接，在轮到它执行时替换旧连接；不会抢占已经在执行的请求。
op=reconnect：立即停止等待当前请求，丢弃旧连接、清空队列并重新认证。等待带相应 id 的 ready 后再发命令。
op=cancel：立即停止等待当前请求，丢弃连接并清空队列，保留 CLI 进程。下一条新请求会重新连接。
op=close：释放连接、取消当前及排队请求，保留 CLI 进程。结束整个会话应关闭 stdin 并等待进程退出。

cancel、reconnect 和 close 控制本地连接。执行中断后，按 execution_state 检查远端进程和业务状态。新连接分配独立 connection_id，每次旧协议执行分配独立终端编号。

三、结果判断及安全重试
ok=true：CLI 收到了完整结果，远端退出码为 0 且未报告执行错误。
execution_state=finished：收到了远端结果。根据退出码、输出及远端状态判断业务结果。
execution_state=not_started：此请求未发送执行。修正参数、确认目标或恢复连接后可以重新提交。
execution_state=unknown：执行期间超时、取消、断线或输入错误。先运行只读检查，核对远端状态后再决定下一步。
retry_safe=true：本次请求未执行。重新提交前检查目标、权限与命令参数。
id 用于匹配请求与结果。需要跨连接去重时，在业务操作中使用业务幂等键。

失败结果带 code、phase、execution_state、retry_safe。阶段包括 request、connect、ssh、target、prepare、upload、start、execution、input、queue。不要按自然语言错误文本决定自动重试。
fatal=false 时会话可继续接收输入。connection_lost=true 时下一条执行请求重新建连。
fatal=true 时关闭输入并等待进程退出，按结果状态决定后续操作。

四、防呆规则
- 每次只允许一个执行请求占用连接，最多另有 16 条未开始的请求。队列满返回 busy，不执行超出的请求。控制请求不进入该队列，可以处理卡住的执行。
- 推荐一次提交一条，等结果再提交下一条。批处理中的命令失败时默认清空队列。
- 只有相互独立的批量检查才使用 session --continue-on-error；连接或传输失败仍取消未发送队列。
- 活跃请求与排队请求不能重复使用相同的非空 id。重复请求被拒绝，原请求继续处理。控制请求可省略 id，或使用新的唯一 id。
- 控制操作只能包含 op 和 id；不会悄悄忽略附带的脚本。拼错字段、非法 Shell、超出时限、脚本与文件同时出现都会在执行前拒绝。
- --id、--script、--command 不能重复指定。--expect-platform 与 --expect-hostname 在每次连接认证后校验目标，不匹配就拒绝执行。hostname 是防误操作条件，不代替加密身份验证。
- 默认执行时限 15 秒，连接认证默认 60 秒；均接受 1–300 秒。新结构化协议在远端执行时限之外另留 25 秒等待结果与清理；旧协议终端启动、上传、启动确认与执行分阶段计时。上传的逐批进展时限不占执行预算。
- 脚本上限 64 KiB；新协议每路输出最多 256 KiB，旧协议合并输出最多 256 KiB。会话输入行也有上限；单行过长或输入读取失败会终止会话，活跃执行记为 unknown。
- 关闭 stdin 后处理已接受的队列再退出。发生过拒绝、执行失败或连接失败的会话最终返回 1；全部成功返回 0。必须同时查看每条结果和进程退出码。

五、恢复流程
参数错误、目标不符、队列满：请求未执行；修正问题后提交新请求。队列满时先等已有结果，避免忙循环。
命令退出非零：检查 stdout/stderr 和退出码；默认排队命令已取消。确认业务状态后提交下一条新命令。
执行超时或中途断线：旧连接丢弃，活跃请求结果 unknown，未发送队列取消。先检查远端任务/文件/服务状态，再决定继续、人工处理或安全重试。
旧连接卡住时发送 op=reconnect，分别读取取消确认和新连接的 ready。新连接认证使用 connect-timeout。
CLI 本身无响应：调用方设置总等待上限（连接、分阶段上传和执行预算加合理余量），先尝试控制操作。仍无响应时只结束由本次调用启动的进程树，然后开新实例。不要终止其他远控窗口或所有同名进程。
恢复失败：保留结构化错误和连接编号；必要时 probe 或用 --relay 做一次有目的的对比。不要无限重连，也不要循环重放未知结果的命令。

六、连接与队列设计
采用明确状态转换：ready → busy → ready；传输异常 → disconnected；显式新请求或 reconnect → 重新认证 → ready。连接由单个执行任务独占，控制通道仍可读取，避免对同一传输并发读写。队列与输出都设置容量限制，避免无限积压。
会话复用参考 OpenSSH 的连接管理、Paramiko 的每命令独立通道和 PowerShell 的会话生命周期。资源由发起的 CLI 进程持有。
旧终端兼容修复：先用短握手关闭输入回显，再发送引导程序；脚本分批确认；输出分段且按窗口确认，避免有界输出队列因回显/突发数据丢失而卡住。Windows 输出记录还必须小于实际终端列宽，避免 ConPTY 滚屏丢失长记录；Bash 输出计数器显式初始化，兼容未定义变量检查。

八、旧 Windows 控制台兼容
旧端 terminal=true、terminal_exec=false 时，CLI 通过交互终端执行。部分 Windows Server 控制台会把每行 512 字符的输入截为 254 字符；修复后的发起端改为每行 128 字符上传，并保持逐批确认、完整 SHA-256 校验和原有容量上限。
部分旧控制台重绘还会在协议标记前留下残余字符、末尾补空格。发起端仅在 Windows 旧协议路径按每次命令随机生成的标记识别记录，去掉协议外围的重绘残留；实际业务输出仍按 Base64 字节解码，空格与中文保持原样。
Server 2019 的旧控制台还可能只保留一屏可见输出，丢失较大窗口中的记录和确认标记。Windows 旧协议每 8 条输出确认一次，记录间保留分隔空行，使一批记录和控制标记落在 24 行的终端视口内；新结构化协议不受此兼容窗口影响。兼容模式的大输出会增加确认往返，按任务选择 60–120 秒执行预算，不要把默认 15 秒用于所有输出规模。
出现 Legacy terminal script checksum mismatch 或退出码正常但输出为空时，先用 --version 识别发起端构建，再用 probe 检查目标终端能力。目标的 terminal 与 terminal_exec 均为 false 时，先在被控端授予终端权限。
校验失败或执行超时时，记录原错误和执行状态，先查询远端业务结果。按任务耗时设置 timeout，使用 phase 区分连接、终端准备、脚本执行和协议校验错误。


九、CLI 管理的 TCP 代理与默认 Bash 通道

新版 exec --shell bash 和 session --shell bash 默认使用 SSH，经 CLI 管理的 GeodomDesk TCP 中继连接目标 Linux 的 127.0.0.1:22。可指定 --ssh-port。Windows PowerShell/pwsh 保留原有终端协议。session 没有指定默认 shell 时保留可混用 Shell 的终端路径；要默认 SSH 请指定 --shell bash 或 --transport ssh。

要求发起端具备系统 OpenSSH 客户端，目标 Linux 开启 SSH 服务并允许 GeodomDesk TCP 转发。SSH 登录账号、密码或私钥与 GeodomDesk 账号、设备访问密码分别验证。默认 SSH 用户名取已认证目标的 username，可用 --ssh-user 指定。默认使用 SSH agent/系统默认私钥；密码通过 --ask-ssh-password 无回显输入，自动化由受控进程提供 GEODOMDESK_SSH_PASSWORD，不能写入命令参数、日志或技能。私钥用 --ssh-identity PATH。带口令的私钥先在 SSH agent 中解锁，账号密码变量不充当私钥口令；显式私钥优先尝试，随后才使用本次提供的 SSH 账号密码。

示例：
geodomdesk-cli exec --id DEVICE_ID --shell bash --ssh-user LOGIN --ask-ssh-password --command 'pwd' --json --expect-platform Linux --expect-hostname EXPECTED_HOST
geodomdesk-cli session --id DEVICE_ID --shell bash --ssh-user LOGIN --non-interactive
geodomdesk-cli probe --id DEVICE_ID --transport ssh --ssh-user LOGIN --non-interactive

显式使用原有终端：
geodomdesk-cli exec --id DEVICE_ID --transport terminal --shell bash --command 'pwd' --json --non-interactive

默认 SSH 的认证或启动失败不会自动降级；发送过脚本后断线不会切换通道重跑。先解决缺失的服务、权限或凭据，再明确发起新请求。--transport terminal 是调用前的显式选择，不是断线后的自动重放机制。

每个 Bash 会话复用一个 SSH 进程、一个加密 SSH 连接及其托管隧道。每条脚本使用独立 Bash 进程，目录和变量不继承。输出和错误分开编码，保留退出码；普通 exit 124 能与远端超时区别。Bash 启动时隔离 BASH_ENV、ENV、SHELLOPTS、BASHOPTS，避免发起进程/旧终端的严格模式影响协议与脚本默认行为。脚本自己设置的严格模式仍然有效。

Windows 固定使用系统 OpenSSH Client；中文目录中的助手通过文件名和工作目录启动，避免系统组件对中文绝对路径的处理问题。私钥与可信主机文件路径先解析为绝对路径。

SSH 使用按设备 ID 和 SSH 端口绑定的稳定主机别名，避免随机本地端口导致每次都出现新目标。默认将首次密钥保存在独立 cli-ssh-known_hosts 文件，后续密钥变化拒绝连接。--ssh-known-hosts 指定已有可信文件，--ssh-strict-host-key 要求事先信任的密钥。不要自动删除冲突记录或关闭密钥检查；先核实目标更换原因。

十、通用端口代理

geodomdesk-cli tunnel open --id DEVICE_ID --remote-host 127.0.0.1 --remote-port 22 --local-port 0 --non-interactive
geodomdesk-cli tunnel list --id DEVICE_ID
geodomdesk-cli tunnel close --id DEVICE_ID --tunnel-id TUNNEL_UUID

open 默认分配空闲端口，仅监听发起端 127.0.0.1，默认强制经中继。指定的本地端口被占用时直接失败，不挤掉已有隧道。remote-host 是目标机可访问的主机，不是发起端主机。每个映射最多接受 16 个同时进行的 TCP 连接；新连接独立认证，一个通道失败不重放其他通道的数据。

等待 tunnel_ready 后读取 local_port/tunnel_id。open 是前台受管进程，自动化需要保持 stdin 打开；stdin EOF、Ctrl+C、正常退出会关闭它创建的映射。向 stdin 发送 JSON Lines：
{"op":"status"}
{"op":"close"}

调用其他工具访问端口时，保留隧道进程与三个管道。工具退出后发送 close 或关闭 stdin，并等待隧道进程退出。空闲预连接最多保留 5 秒，下次实际访问重新认证。转发写入连续 30 秒无进展时关闭对应数据通道，并将错误记入 last_error。

通用 TCP 隧道沿用客户端原始转发协议。默认 Bash 在隧道内使用 SSH，代理其他服务时按服务配置 SSH、HTTPS 或 TLS。

十一、客户端可见性与所有权闭环

在同一操作系统、同一登录用户及配置目录下，打开新版客户端对应设备的“TCP 隧道”页面可看到 CLI 创建的映射，标有 CLI、监听/使用中/状态不可用、本地端口与远端地址端口；鼠标提示显示隧道 UUID 和进程。关闭按钮通过对应隧道的控制接口通知其所有者，关闭该映射及其数据通道。手工保存的映射不写入 CLI 注册表，不会被 CLI 清理。

CLI 映射在独立目录注册 UUID、所有者、地址及本地控制端口。状态和关闭请求通过随机挑战与 HMAC 验证隧道所有者。list、ready 和界面仅展示状态信息。控制口拒绝连接时清理过期记录，应答超时时保留记录并显示状态不可用。close 对已清理的 UUID 可重复调用。

Linux SSH 子进程设父进程死亡信号；Windows 启动器先把自己加入关闭即终止的进程作业，再启动主程序及 SSH 子进程。正常关闭由资源所有者释放，强制结束后操作系统关闭端口，下次 list 清理遗留注册记录。

CLI 进程持有映射，关闭发起端 TCP 页面后继续转发。点击某条 CLI 隧道的关闭按钮会中断对应 Bash 会话，空闲时报告 connection_lost，执行中报告 unknown。下一条新请求或显式 reconnect/fresh 可创建新隧道。

ready 和 exec 结果中的 tunnel 记录当时状态。使用 tunnel list 或刷新客户端页面获取实时状态。--version 包含构建号，ready 提供 cli_version 和 cli_build。

十二、连接与执行超时

终端及隧道认证采用一个总连接预算内最多三次新握手；预算不足 10 秒只尝试一次，10–14 秒最多两次，15 秒以上最多三次。每次都保留独立时间片，避免首次卡住耗尽总预算。仅对明确的临时传输故障重建，不重试错误凭据、目标不匹配或权限拒绝。显式设备密码、管理员凭据或 GEODOMDESK_DEVICE_CODE 仅使用一次完整预算的登录尝试，避免登录响应丢失后重复提交凭据。认证拒绝标记为 phase=authentication，不作为自动重连条件。旧终端在上传脚本之前的 prepare 阶段断线可重建一次；upload/start/execution 阶段不自动重放。失败历史通过 setup_errors 返回；长会话保留最近 6 条，完整历史由调用方保存事件及诊断流。

SSH 首次启动预算包括隧道认证、SSH 登录和工作进程 ready。执行使用独立超时和输出上限。收到远端超时结果或 unknown 时，按恢复流程检查业务状态。

原始 TCP 转发按完整连接关闭。代理服务优先使用 SSH、长度字段或显式消息分帧。使用 TCP 半关闭表示请求结束的服务，接入前验证协议适配。

工程验证应包含：真实 CLI 默认/显式路径、Windows 与 Linux 目标、Unicode/退出码、脚本和输出边界、连接复用与 fresh、取消和队列、错误凭据与密钥变化、进程崩溃、注册清理、界面关闭仅作用于对应所有者。先本地编译和验证，再推送构建；发布时核对全部平台产物、签名元数据和云端完整文件摘要。

十三、完整客户端的界面接口验证

本项目的 FRB 1.x 普通 Rust 接口在工作线程执行，并向 Dart 返回 Future。隧道列表与关闭接口返回具体 String，在该工作线程内使用短生命周期的当前线程运行时等待本地控制调用；不要直接暴露 async Rust 函数，让生成器把 Future 当成字符串返回。
使用 CI 生成的桥接源码，启用 flutter 功能编译完整核心库，再运行各平台原生构建和安装包测试。

十四、隧道闭环复核与故障恢复

设备 ID 可以按客户端显示带空格粘贴，open、list、close 对数字 ID 使用相同规则。控制口建立连接与收到应答分别计时：最多等待 3 秒连接，连接后应答预算 400 毫秒。Windows 实测本地关闭端口约 2 秒才返回拒绝连接；仅在确认控制口拒绝连接后清理过期记录，超时仍保留状态不可用，避免误判所有者已退出。
所有者崩溃后可以直接 close，不用先 list；已确认端口关闭时返回 already_closed 并清理注册。有效关闭请求一旦被所有者接受，即使应答无法送达也会释放数据通道。网络复位可能连请求本身都没送达；这时先查询，或按原 UUID 再发一次幂等 close，不重跑任何业务脚本。
在客户端页面验证隧道生命周期。用 CLI 创建映射，检查对应行和数据通道的使用中状态。点击关闭后核对 CLI 返回、数据 EOF、端口与注册清理、手工映射保留。正式发布前执行各平台构建和 Windows 崩溃回归。
